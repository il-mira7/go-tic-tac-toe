# 🎮 go-tic-tac-toe

Крестики-нолики на Go: можно играть против идеального бота — ход за него выбирает алгоритм **минимакс**, сыграть вничью уже хороший результат — или против другого человека в партиях на двоих. У каждого игрока аккаунт: регистрация, вход, партия привязана к пользователям.

Одностраничный интерфейс встроен в бинарник через `embed`, REST API — на gin, граф зависимостей собирается uber-fx, пароли хранятся как bcrypt-хеши, состояние партий — в PostgreSQL.

## Запуск

Понадобятся Go 1.25+ и запущенный PostgreSQL:

```bash
createdb tictactoe_db            # схема создастся сама при первом старте
cp .env.example src/.env         # и впишите в него свой DATABASE_URL
cd src
go run ./cmd/app
```

Открыть [http://localhost:8080](http://localhost:8080). Порт переопределяется переменной `PORT`.

## API

Все руты, кроме регистрации и входа, требуют Basic-auth (логин:пароль).

| Метод | Рут | Описание |
|-------|-----|----------|
| `POST /signup` | регистрация (логин от 3 символов, пароль от 6) |
| `POST /login` | вход, возвращает uuid пользователя |
| `POST /game/create` | создать партию: `{is_vs_bot: true}` — против бота, иначе ждать второго игрока |
| `GET /games/available` | список партий, куда можно присоединиться |
| `POST /game/:uuid/join` | присоединиться к чужой партии |
| `POST /game/:uuid` | ход: `{board, row, col}` → новое состояние партии |
| `GET /game/:uuid` | текущее состояние партии |
| `GET /user/:uuid` | профиль пользователя |

Клиент присылает поле целиком, сервер проверяет, что предыдущие ходы не подменены, фиксирует ход и отвечает ходом соперника (в партии с ботом соперник — минимакс, играющий за системного пользователя `bot`).

## Архитектура

Слоистая структура зафиксирована учебным заданием (Go Bootcamp, School 21): domain → infrastructure → web плюс DI-слой, интерфейсы на каждом шве и мапперы между представлениями данных.

```
src/
├── cmd/app/            — точка входа, загрузка .env
├── internal/
│   ├── app/            — менеджер партий: создание, присоединение, ходы
│   ├── domain/         — правила игры, минимакс, пользователи, контракты сервисов
│   ├── infrastructure/ — PostgreSQL (pgxpool), репозитории, мапперы
│   ├── web/            — gin-сервер, хендлеры, basic-auth middleware, UI
│   └── di/             — сборка зависимостей (uber-fx)
└── public/             — index.html, встраивается в бинарник
```

Схема БД (`users`, `games`) описана в `init.sql`, встроен в бинарник и применяется при старте — отдельные миграции не нужны.

## Что я сделала бы иначе

- Для приложения такого размера слоёв многовато: в этом этапе их стало уже пять (добавился app-менеджер партий). Хватило бы `web → domain → хранилище` с одним интерфейсом на границе хранилища.
- Модель игры маленькая, а представлений у неё три (domain, storage, web) — мапперы между ними здесь проще схлопнуть.
- Контракты сервисов лежат одним файлом `interfaces/service.go`: добавляя пользователей, я трогала тот же файл, что и для игры, — при росте проекта такие «общие» файлы становятся точкой постоянных конфликтов.
- При этом интерфейс репозитория себя оправдал: хранилище сменилось с `sync.Map` на PostgreSQL без изменений в домене.
